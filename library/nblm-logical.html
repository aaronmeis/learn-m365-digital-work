Logical Architecture View: Microsoft's Digital-Work Platform

1. System Context & Architectural Boundaries

1.1 Scope and Domain Separation

The logical architecture of Microsoft's Digital-Work Platform defines the functional boundaries, logical components, entity models, and communication flows required to enable enterprise collaboration, digital business processes, and software delivery.

The enterprise system topology is logically partitioned into two domain boundaries: * Digital-Work Platform: Encompasses business communications, document management, enterprise search, productivity applications, low-code business process automation, and organizational knowledge graphs (realized via Microsoft Exchange, Teams, SharePoint, OneDrive, Power Platform, Dataverse, and Microsoft Graph). * Software-Delivery Platform: Encompasses source code governance, pull request reviews, CI/CD automation pipelines, security scanning, release deployment, and engineering evidence stores (realized via GitHub Repositories, Issues, Pull Requests, Actions, Packages, and Projects).

Core Architectural Principle: Copilot is a user-facing intelligence/orchestration layer, not the integration layer itself. The durable integration assets are APIs, event streams, identity relationships, connectors, schemas, service contracts, and policy controls beneath it.

To prevent ungoverned data duplication and preserve clear data ownership, specific authoritative systems of record are designated across domains:

2.2 Copilot Integration Enablement Layer

To mitigate point-to-point integration sprawl and prevent unauthorized AI data access, the target-state logical architecture establishes a Copilot Integration Enablement Layer. This middleware control plane governs interactions between AI interaction surfaces (Microsoft 365 Copilot, GitHub Copilot, custom agents) and enterprise systems of record.

The enablement layer structures operations across three functional planes:

  • Control Plane Sub-functions:

    • MCP Gateway / Catalog: Functions as the authoritative enterprise registry for approved Model Context Protocol (MCP) servers, tools, and prompts. Enforces tool availability based on organization policy and prevents unauthorized local or remote server registration.
    • API Gateway: Coordinates API routing, authentication token exchange, rate limiting, quota enforcement, and circuit breaking across external integrations.
    • Connector Lifecycle Manager: Administers the provisioning, admin/user consent workflows, schema definition registration, delta-sync schedules, and deprecation of synced and federated connectors.
    • Agent Policy Enforcement: Evaluates runtime security policies, tool execution allowlists, and prompt-injection defense mechanisms. Enforces strict boundary separation between retrieved untrusted content and system instructions, and integrates automated secret scanning (such as Push Protection) to block secrets in AI responses or automated tool calls.
    • Workflow / Approval Engine: Intercepts state-changing tool requests generated by AI agents. Enforces deterministic workflow gates requiring explicit human-in-the-loop confirmation before initiating write, update, delete, or deployment transactions.
    • Audit / Telemetry Pipeline: Ingests structured telemetry streams covering tool calls, parameters, identity contexts, model reasoning outcomes, citations, and system errors, routing them directly into enterprise SIEM/SOAR platforms.

  • Knowledge Plane Sub-functions:

    • Search & Graph Indexing: Houses Microsoft Graph semantic indexes, full-text search indexes, and vector stores for passive, highly performant knowledge discovery and grounding.
    • Synced Connector Ingestion: Manages bulk crawl, delta fetch, and content normalization pipelines that populate the Knowledge Plane.

  • Transaction Plane Sub-functions:

    • API & Workflow Execution: Hosts real-time REST, GraphQL, and MCP tool call execution pathways that interact with operational databases.
    • Event & Message Queuing: Coordinates asynchronous pub/sub messaging, webhook event dispatches, and CI/CD status updates.

3.2 Authorization & Permission Models

Logical governance across the Digital-Work Platform rests on five fundamental security constraints:

  1. Permission Fidelity in Synced Connectors: When external knowledge is indexed into Microsoft Graph via synced connectors, source-system access control lists must be accurately mapped into equivalent Microsoft Graph user-context ACLs. Microsoft 365 Copilot dynamically enforces permission trimming against these ACLs; any failure in permission fidelity creates severe data oversharing risks.
  2. Scope Distinction in Synced Ingestion:
    • Tenant-Configured Synced Connectors: Provisioned by central administrators for enterprise-wide data sources (e.g., ServiceNow knowledge bases, Confluence repositories). Indexed data is globally retrievable by any user possessing source-system entitlements.
    • Self-Serve Synced Connectors: Enabled by admins but configured individually by end users. Synchronization is restricted to personally relevant content using the user's personal credentials, and indexed items are scoped strictly to that specific user's identity context. Disconnection automatically purges user-scoped index data.
  3. Delegated Context vs. Application Identity:
    • Delegated (User-Context) Authorization: Mandatory for user-initiated queries (e.g., Copilot Chat, live federated MCP queries, Work IQ reasoning). Entitlements are evaluated dynamically at runtime against the authenticated user's Entra ID identity token.
    • Application / Workload Identity Authorization: Utilized for automated, asynchronous server-to-server workflows (e.g., CI/CD pipelines, background synchronization, webhook processing). Operates via managed identities, certificates, or short-lived tokens (such as GitHub App installation tokens) with restricted scope.
  4. Logical Separation of Read-Only vs. Write-Capable Tools: Tools registered in the MCP catalog or agent runtimes must explicitly segregate read-only retrieval mechanisms from write or action execution endpoints. Consequential state updates cannot be executed directly by natural-language model output; they must pass through deterministic validation gates.
  5. Runtime Security Controls and Threat Defense: All tool execution pathways must incorporate active runtime defenses. Prompts and retrieved context must be structurally separated to prevent prompt-injection attacks. Automated secret scanning (e.g., GitHub Push Protection) must analyze tool inputs and generated outputs to prevent credential leakage in automated code generation or ticket creation.

4.2 Detailed Sequence Analysis

Flow A: Live Federated Context Retrieval via MCP

  1. User Prompt Submission: An authenticated end user submits a natural-language query to Microsoft 365 Copilot Chat (e.g., "Retrieve the live status and recent incident logs for Order-Service from ServiceNow").
  2. Reasoning & Work IQ Assembly: Microsoft 365 Copilot invokes the Microsoft Work IQ API to evaluate the user's signed-in context, identify required data sources, and target an approved Federated MCP Connector.
  3. Control Plane Verification: The request is routed to the Copilot Integration Enablement Layer. The layer validates:
    • The user's delegated Entra ID OAuth 2.0 bearer token.
    • That the targeted MCP Tool is registered and marked Active in the central MCP Catalog.
    • That the user possesses authorized execution rights for the requested data classification.
  4. Live Federated Request Execution: The Federated MCP Connector executes an HTTPS request to the external system's MCP server endpoint using the user's delegated identity context.
  5. Source Authorization & Execution: The target system authenticates the request, evaluates source-level entitlements, executes the read operation, and returns a real-time data payload containing status details and resource URLs. No data is stored or indexed into Microsoft Graph.
  6. Response Grounding & Citation: Microsoft 365 Copilot synthesizes the real-time payload into a natural-language response, attaches source citations, and returns the grounded answer to the user interface while emitting session telemetry to the audit pipeline.

Flow B: Event-Driven Lifecycle Action

  1. Repository Event Emission: A software developer pushes commits or opens a Pull Request within a GitHub repository.
  2. Webhook Dispatch: GitHub generates an event payload containing commit hashes, pull request metadata, and author details, sending it via an authenticated webhook to the Integration Gateway.
  3. Parallel Gate Processing: The Integration Gateway validates the webhook HMAC signature and dispatches the event in parallel to subscribed operational engines:
    • Static Security Analysis (SAST): Initiates automated vulnerability and secret scanning scans.
    • Change Management Engine: Automatically logs or updates an operational change request in ServiceNow.
    • Architecture Governance: Validates architectural scorecards and compliance standards.
  4. System of Record Logging: Downstream tools execute their respective scans, update their authoritative databases, and generate an immutable evidence URL.
  5. Asynchronous Check Status Post: Each processing engine calls the GitHub Checks API asynchronously, posting its individual execution result (Pass/Fail) and evidence link back to the specific pull request commit.
  6. Branch Protection Gate Enforcement: GitHub aggregates all Check Run statuses. The repository branch protection rules evaluate the aggregated results against configured policy rules, deterministically enabling or blocking the pull request merge capability without relying on autonomous AI model state management.

5. Architectural Decision Rules & Trade-offs

5.1 Synced vs. Federated Data Access Framework

Selecting between data ingestion (synced connectors) and real-time retrieval (federated MCP connectors) requires balancing specific operational criteria:

Synced / Indexed Knowledge (Microsoft Graph) Federated / MCP Real-time Access
Data Freshness: Near-real-time to periodic batch. Bounded by crawl schedules and delta fetch intervals. Data Freshness: Instantaneous. Queries live source endpoints dynamically at execution time.
Search & Discovery Quality: High. Full-text and semantic vector indexing in Microsoft Graph enables enterprise-wide cross-domain discovery and ranking. Search & Discovery Quality: Targeted. Retrieval is parameter-driven and restricted to specific tool interfaces exposed by the MCP server.
Data Sensitivity & Volume: Optimal for high-volume, semi-static enterprise content where centralized secondary indexing is permissible. Data Sensitivity & Volume: Optimal for highly sensitive, regulated, or massive datasets that must remain in their authoritative source.
Write / Action Capabilities: Read-Only. Synced indexes serve strictly as passive knowledge bases for search and AI grounding. Write / Action Capabilities: Natively Read-Only by default for context retrieval. Write, update, and delete actions require explicit MCP capability rollout, gated by catalog policies and human workflow approvals.
System of Record Impact: Minimal runtime query impact on source system APIs after initial ingestion crawl completes. System of Record Impact: Direct runtime impact. Frequent AI queries impose continuous API request load on target source systems.

5.2 System State & Action Governance Principles

  • Transactional Authority Owned by Target Platform APIs: System state transitions (e.g., merging code, closing an incident, approving a change record, triggering a production deployment) must remain strictly owned by target platform APIs, event buses, and deterministic rules (e.g., GitHub branch protection, pipeline gates). AI models and agents must never act as autonomous, unvalidated state managers.
  • Mandatory Human Confirmation for Consequential Actions: Any AI-driven action classified as consequential—defined as operations that create, modify, delete, deploy, or transfer enterprise data—requires explicit human confirmation or a deterministic workflow approval step prior to transaction execution.
  • Policy Enforcement External to Model Reasoning: Security policies, tool allowlists, rate limits, and access controls must be enforced within the API gateway, integration gateway, workflow engine, and identity platform. Security rules must reside outside the LLM layer to ensure prompt text cannot bypass enterprise controls.
