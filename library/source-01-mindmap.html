Mind map — Microsoft's Digital-Work Platform

From an integration-architecture perspective, Microsoft 365 is a digital-work platform with Microsoft Graph as its API/data plane, while GitHub is a software-delivery platform with GitHub APIs, webhooks, Actions, and MCP as its extension plane. Microsoft 365 Copilot and GitHub Copilot sit above those platforms as AI interaction and orchestration layers; third parties integrate through APIs, connectors, agents, events, identity federation, and—now increasingly—Model Context Protocol (MCP). learn.microsoft

The key architectural correction is this: Copilot is not the integration layer itself. Copilot is a user-facing intelligence/orchestration layer. The durable integration assets are APIs, event streams, identity relationships, connectors, schemas, service contracts, and policy controls beneath it.

The third-party integration models

There are five core ways a third party can integrate. Choose the model based on whether the AI needs knowledge, real-time facts, actions, or workflow automation.

Integration model Data movement Primary use Example
API consumption Application calls a third-party API at request time Transactional read/write and system automation A Teams app retrieves a customer record from Salesforce
Event-driven integration Source publishes webhook/event; consumer processes it Near-real-time state synchronization and workflow initiation A GitHub pull-request event creates or updates a ServiceNow change record
Indexed knowledge connector Third-party content is copied/indexed into Microsoft Graph Enterprise search, retrieval, and Copilot grounding Index technical runbooks from GitHub, Confluence, or a document system
Federated MCP connector Data is fetched live without copying it to Microsoft Graph Real-time facts and, where enabled, actions Ask Copilot for current incident status from an ITSM platform
Agent/tool integration An agent invokes governed actions or workflows Multi-step task execution A Copilot Studio agent validates a request, creates a ticket, asks for approval, then updates a record

The architectural decision is often simple:

  • Use synced/indexed content when discovery, search quality, and repeated knowledge retrieval matter more than instantaneous freshness.
  • Use federated/MCP access when data is highly dynamic, sensitive, too large to duplicate, or must remain in its authoritative source.
  • Use API/workflow actions when the integration changes state.
  • Use webhooks/events when systems must react to a change instead of polling.

Microsoft's current connector model explicitly distinguishes synced connectors, which ingest and index external content into Microsoft Graph, from federated connectors, which use MCP to retrieve external data live without storing it in Graph. learn.microsoft

Microsoft 365 Copilot third parties

1. Synced connectors: third-party knowledge into Graph

A synced Microsoft 365 Copilot connector ingests content from an external platform into a Microsoft Graph external connection. Each indexed item should include:

  • Content or extracted text
  • Metadata, such as title, URL, content type, author, timestamps, tags, and business identifiers
  • An access control list that maps source-system entitlements to the Microsoft 365 user context
  • Semantic labels that improve retrieval and Copilot understanding

Examples include GitHub Markdown documentation, Confluence knowledge, ServiceNow knowledge articles, policy repositories, PLM artifacts, CRM records, or controlled engineering documentation.

The non-negotiable requirement is permission fidelity. If the connector indexes a source document but fails to model the source authorization correctly, Copilot can amplify an existing data-exposure problem. Microsoft's connector documentation states that indexed items include an ACL specifically to enforce permissions. learn.microsoft

This approach is strong when:

  • The data changes rapidly.
  • The authoritative system must retain control.
  • Duplicating regulated, controlled, or sensitive records into a secondary index is undesirable.
  • The use case requires not only reading but a carefully governed action, such as creating a ticket or updating a case.

Microsoft states that federated connector content is returned in real time, is not synchronized into Microsoft Graph, and can support write, update, and delete actions through MCP-based connector capabilities. learn.microsoft

3. Build versus buy

For Microsoft 365 Copilot connectors:

  • Use a Microsoft or partner prebuilt connector when it meets security, coverage, permission, lifecycle, and support requirements.
  • Build a custom synced connector when the source is proprietary, permission semantics are specialized, or domain metadata must be represented precisely.
  • Build a federated MCP connector when real-time data, external-system authority, and controlled actions are the priorities.
  • Use Copilot Studio for low-code agent experiences and Power Platform-native workflow orchestration.
  • Use Microsoft 365 Agents Toolkit / custom-engine agent approaches when you need professional-code agent logic, deeper custom orchestration, or a productized enterprise agent.

Microsoft notes that custom synced connectors can be built with the Microsoft 365 Agents Toolkit, connector SDK, or Copilot connector APIs; they require application registration and administrator consent for appropriate Microsoft Graph permissions. learn.microsoft

The MCP server exposes defined resources, prompts, and/or tools. A tool can return data, call an API, or take an action. The agent can then use returned information to plan or generate a code change.

Example:

"Investigate production errors for orders-api, identify the relevant error-handling path, propose a patch, add regression tests, and open a draft pull request."

A governed implementation can allow GitHub Copilot to:

  1. Use an observability MCP server to retrieve traces and errors.
  2. Use GitHub repository context to identify affected code.
  3. Generate a patch and tests locally or in an approved agent environment.
  4. Run tests and static analysis.
  5. Create a draft PR.
  6. Require human review, automated quality gates, and branch protection before merge.

GitHub documentation states that organizations can create MCP servers tailored to their needs and integrate them with Copilot Chat. docs.github

GitHub App versus OAuth app

For third-party GitHub integration, the default enterprise recommendation is usually a GitHub App, not a broad OAuth app.

Choice Identity model Security posture Best fit
GitHub App App installation; fine-grained repository and organization permissions; short-lived installation tokens Stronger default for server-to-server integration CI/CD vendors, security tools, ITSM, deployment systems, compliance platforms
OAuth app User authorizes scopes; normally acts in user context Useful but can create broad delegated scope User-facing SaaS integrations and personal workflow tools
Personal access token Human or machine token, depending on type Avoid for durable enterprise service integration where possible Temporary development, tightly controlled automation, exceptional legacy scenarios

Architecturally, use a GitHub App when a platform needs to receive GitHub webhooks and act across approved repositories with narrowly scoped permissions. Use OAuth when the external app genuinely needs to operate on behalf of an individual user.

Microsoft 365 work into GitHub delivery

The inverse direction typically uses Teams apps, Power Automate, GitHub Apps, or middleware—rather than GitHub Copilot directly.

Examples:

  • An approved Teams/Power Automate request creates a GitHub issue from a standardized intake form.
  • A GitHub release or deployment sends an adaptive-card notification to a Teams channel.
  • A pull-request approval workflow triggers a ServiceNow change-control step, with status mirrored back into GitHub.
  • Architecture decisions recorded in SharePoint or a controlled knowledge base are referenced in GitHub issue templates or engineering standards checks.
  • Security or compliance approvals in Microsoft 365 initiate promotion gates in GitHub Actions.

Security architecture

For a regulated enterprise—particularly one handling CUI, export-controlled content, or safety-critical engineering—the integration design should begin with trust boundaries, not prompts.

Identity and authorization

  • Federate user identity through Entra ID where possible using OpenID Connect or SAML.
  • Automate joiner-mover-leaver lifecycle with SCIM.
  • Prefer delegated, user-context authorization for user-requested retrieval where entitlement must be evaluated dynamically.
  • Prefer managed application identities, workload identities, certificates, and short-lived tokens for service-to-service workloads.
  • Use least-privilege scopes; separate read/search permissions from write/action permissions.
  • Maintain distinct application registrations and credentials across development, test, staging, and production.
  • Avoid generic shared accounts and long-lived static tokens.

Data and content controls

  • Classify data before indexing it into Copilot-accessible stores.
  • Map third-party entitlements precisely into connector ACLs.
  • Decide explicitly whether content is copied, cached, indexed, or retrieved live.
  • Establish an allowed-data policy for each integration: public, internal, confidential, regulated, export-controlled, CUI, or prohibited.
  • Ensure deletions, permission changes, and legal holds propagate correctly to indexes, caches, downstream stores, and AI retrieval layers.
  • Configure retention and audit requirements for prompts, responses, actions, and source citations.

Agent and MCP controls

  • Treat each MCP server as a production integration endpoint, not as a convenience plugin.
  • Establish a centrally managed MCP catalog with owner, purpose, data classification, action permissions, authentication method, logs, lifecycle state, and approval date.
  • Separate read-only tools from write-capable tools.
  • Require user confirmation or a workflow approval for consequential actions: create, modify, delete, deploy, approve, or transmit.
  • Bind actions to verified identity and scoped authorization; do not rely on a natural-language request alone.
  • Protect against prompt injection from external content by separating retrieved content from system instructions, validating parameters, allowlisting tools, and enforcing action policy outside the model.
  • Log tool calls, parameters, identity, decision outcome, response references, and error conditions into an auditable telemetry pipeline.

Integration decision framework

Use this architecture decision sequence for every third-party integration:

  1. What is the system of record? Do not create a second authoritative copy merely to make it "AI accessible."

  2. Is the use case retrieval, recommendation, action, or orchestration? Retrieval generally fits search, connectors, or MCP. Actions require APIs, workflows, authorization, approval, and audit.

  3. Does the data need to be indexed or retrieved live? Use indexing for durable knowledge and broad discovery. Use live federation for freshness, source control, and transaction-like context.

  4. Whose permissions should apply? User-delegated, service-delegated, application-only, or a hybrid model each create different risk and operational implications.

  5. What is the blast radius of a wrong response or wrong action? Read-only retrieval is lower risk than ticket creation; ticket creation is lower risk than production deployment or record deletion.

  6. Where does policy enforcement occur? Enforce policy in the API gateway, integration service, workflow, identity platform, and target system—not only in agent instructions.

  7. What evidence is required? Record prompts, source citations, tool decisions, approvals, resulting transaction IDs, test outcomes, and lifecycle traceability.

Recommended target state

For an enterprise integration architecture, establish a Copilot Integration Enablement Layer rather than allowing point-to-point AI connections.

                           ┌────────────────────────────┐
                           │ AI / Copilot experiences    │
                           │ M365 Copilot │ GitHub Copilot│
                           │ Copilot Studio │ custom apps │
                           └──────────────┬─────────────┘
                                          │
                  ┌───────────────────────▼───────────────────────┐
                  │ Copilot Integration Enablement Layer           │
                  │ MCP gateway / catalog │ API gateway            │

                  │ Workflow / approval │ Audit / telemetry        │
                  │ Schema registry │ secrets │ service identities  │
                  └───────────────┬────────────────────┬──────────┘
                                  │                    │
                       ┌──────────▼──────────┐ ┌──────▼───────────┐
                       │ Knowledge plane      │ │ Transaction plane │
                       │ Search / Graph index │ │ APIs / workflows  │

                       └──────────┬──────────┘ └──────┬───────────┘
                                  │                    │
                ┌─────────────────▼────────────────────▼─────────────────┐
                │ Enterprise systems of record and third-party platforms  │
                │ GitHub │ ITSM │ CRM │ ERP │ PLM │ Data │ Observability  │
                └────────────────────────────────────────────────────────┘

This gives you a disciplined separation:

  • Knowledge plane: curated information made retrievable to people and AI.
  • Transaction plane: controlled APIs and workflows that can alter system state.
  • Control plane: identity, access, policy, secrets, observability, audit, and lifecycle governance.

For your architecture work, the most important design principle is: make AI a governed consumer and orchestrator of enterprise integrations, not a bypass around integration, authorization, and control architecture.
