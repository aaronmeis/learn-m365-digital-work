Physical Architecture View: Microsoft's Digital-Work Platform

1. Architectural Scope & Physical Topology Overview

The physical infrastructure scope of Microsoft's Digital-Work Platform spans three distinct hosting boundaries: Microsoft-managed multi-tenant cloud services (Microsoft Graph REST/GraphQL endpoints, Microsoft 365 Copilot runtime engines, Microsoft Search, Copilot Studio runtime, and the Microsoft Work IQ API intelligence layer), customer-hosted environments (on-premises Microsoft Graph connector agents, local workstation sandboxes, customer Virtual Private Cloud [VPC] host nodes, and remote Model Context Protocol [MCP] server instances), and third-party/external platforms (GitHub Cloud / GitHub Enterprise Server [GHES], enterprise SaaS applications like ServiceNow, Salesforce, and Jira, and external SIEM/SOAR observability pipelines).

This document details the concrete physical realization (altitude) of the platform's logical capabilities. It specifies the actual physical service endpoints, software agent topologies, host execution sandboxes, persistent data stores, hardware/compute isolation boundaries, open networking standards, and sovereign government cloud variant configurations as defined strictly within the platform baseline.

3. On-Premises & Hybrid Deployment Components

Bridging private enterprise data centers with cloud-hosted AI orchestration layers requires specific software binaries, host sandboxes, network transport paths, and identity execution models.

Microsoft Graph Connector Agent Topology & Execution Contexts

  • Physical Role & Ingestion Mechanics: Installed as a dedicated Windows service or Linux binary on customer-managed virtual or physical servers inside private network boundaries. It crawls local data repositories (e.g., SMB/NFS file shares, local SQL databases, intranet portals), extracts text, extracts metadata, normalizes schema definitions, translates source Access Control Lists (ACLs) into Entra ID security identifiers, and securely pushes structured externalItems up to the Microsoft Graph index over outbound HTTPS (TCP 443).
  • Self-Serve vs. Tenant-Wide Ingestion Topologies:
  • Tenant-Configured Synced Connectors: Deployed by enterprise administrators using system credentials or app-only identities. They perform continuous scheduled delta crawls across enterprise-wide repositories, maintaining persistent index structures in Microsoft Graph.
  • Self-Serve Synced Connectors: Enabled by admins but configured by individual end users. They run strictly within the authenticated user's personal OAuth context, crawling a limited window of recent personal content. Crucially, when a user disconnects the connector or an admin disables it, all indexed content associated with that instance is automatically purged from the Microsoft Graph index.
  • Identity Plane Boundaries (Delegated vs. Application-Only Context):
  • User-Delegated Context: Used during live query processing and self-serve connector ingestion. The application executes using the signed-in user's token. Entitlement evaluation occurs dynamically at runtime, ensuring the system can never retrieve or index content beyond the user's explicit effective permissions.
  • Application-Only Context: Used by tenant-configured scheduled background ingestion agents. The connector operates using a dedicated service principal identity with pre-consented Graph permissions (ExternalItem.ReadWrite.All). Security is maintained by requiring the connector to explicitly extract local ACLs and attach them to each ingested externalItem, allowing Microsoft Graph to enforce permission trimming at runtime.

Local vs. Remote Model Context Protocol (MCP) Server Hosting

  • Local MCP Servers: Executed directly on developer workstations within IDE processes (VS Code, Visual Studio, JetBrains, Xcode), local sandboxes, or the GitHub Copilot CLI runtime. Communication occurs locally via standard input/output (stdio) streams or local Inter-Process Communication (IPC).
  • Remote MCP Servers: Production-grade integration endpoints deployed inside customer VPCs, hybrid data centers, or vendor SaaS clouds. Remote MCP servers are registered within an enterprise catalog and accessed over secure HTTPS/OAuth network paths. They process real-time queries without duplicating source data into Microsoft Graph.

Developer Tooling, Runtime Discovery, and Security Controls

  • Work IQ Dev Tools (wiqd CLI): A specialized command-line utility used by developers across the entire declarative agent lifecycle—scaffolding, manifest validation, cloud provisioning, packaging, publishing, and telemetry monitoring.
  • Agentic Resource Discovery (ARD) & Agent Finder: Runtime discovery service implementing the open ARD specification. The client uses the Agent Finder skill, stored physically on local file systems at ~/.copilot/skills/github-copilot/SKILL.md, to dynamically locate, rank, and connect to remote MCP servers, tools, and agents based on user prompt intent.
  • GitHub MCP Security Mechanics:
  • Push Protection: Built-in security control that inspects AI-generated code and tool responses before transmission, blocking exposed credentials, tokens, and private keys from being executed or committed.
  • GitHub Advanced Security (GHAS) Integration: Remote and local MCP servers integrate directly with GHAS secret scanning pipelines, enabling real-time scanning of AI agent context streams for sensitive corporate data.

6. Licensing Tiers, Administrative Authorization & Governance

Deployment of platform capabilities requires identity registrations, administrative consent, token lifecycle management, and policy enforcement across Entra ID and GitHub administrative planes.

Identity & Consent Surface & Token Mechanics

  1. Entra ID Application Registrations: Custom synced connectors, Copilot APIs, and Work IQ API implementations require service identity registrations in Microsoft Entra ID.
  2. Permission Context & Admin Consent: * Delegated Permissions: Used for real-time user queries. Evaluated dynamically against user token lifetimes and Entra ID Conditional Access Policies (CAP) at runtime. * Application Permissions: Required for background tenant-configured synced connectors (ExternalItem.ReadWrite.All). Requires high-privilege Global Admin or Application Admin consent.
  3. GitHub App Credentials: Preferred over OAuth Apps for server-to-server integrations. Uses short-lived installation access tokens and fine-grained, repository-scoped permissions.

MCP Catalog, Tool Controls, & Blast Radius Management

  • Centralized MCP Governance: Production MCP servers must be cataloged within a central registry with designated ownership, data classification, authentication method, lifecycle state, and approval logging.
  • Blast Radius Reduction (Read vs. Write Tools): Systems must physically segregate read-only tools from write-capable tools. Consequential write/delete/update operations carry elevated risk and require strict governance.
  • Action Approvals & Security Safeguards: Consequential actions cannot be triggered purely via natural language prompts; they require explicit out-of-band user confirmation or workflow approval steps. All MCP tool calls are protected by Push Protection and GHAS secret scanning to prevent credential leakage.

Licensing SKUs & Silence Marking

While administrative consent thresholds and identity registrations are enforced, specific product licensing SKUs (e.g., M365 E3/E5 Copilot Add-ons, standalone Copilot SKUs, or GitHub seat tiers) are silent in the source context.
