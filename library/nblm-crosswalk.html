Enterprise Architecture Framework Crosswalk: Microsoft's Digital-Work Platform

1. Executive Purpose, Methodology, & Abstraction Criteria

This report presents a formal Enterprise Architecture Framework Crosswalk for Microsoft's Digital-Work Platform and its software-delivery extensions. The crosswalk maps integrated platform capabilities, system interfaces, logical data entities, and physical infrastructure realizations to TOGAF ADM Phases (Phases A through D) and DoDAF v2.02 Viewpoints (OV, SV, DIV, StdV).

Abstraction Methodology

To enforce strict structural rigor, architectural artifacts are categorized across three explicit abstraction tiers:

  • Conceptual Tier (What and Why): Establishes high-level operational concepts, capability taxonomies, actors, and domain boundaries without referencing vendor-specific product names, hostnames, or physical SKUs.
  • Logical Tier (Which parts and how they talk): Defines functional components, operational activities, data entities, attributes, and synchronous versus asynchronous resource flows in capability-centric terms.
  • Physical Tier (What is deployed and where): Maps logical entities directly to named cloud services, physical host sites, tenant isolation boundaries, protocols, developer tooling, SKUs, and cloud environment variants.

Rule for Explicit Architectural Silence

In accordance with strict enterprise architecture standards, where the provided source context does not explicitly specify a framework mapping parameter, licensing SKU, retention window, regional data residency boundary, or Government Cloud (GCC, GCC High, DoD, Gov Secret) capability parity, the element is formally classified as "Unsupported by Source / Silent". Missing technical specifications are not inferred or extrapolated.

3. TOGAF ADM Phase & DoDAF Viewpoint Structural Mapping

3.1 Phase A (Architecture Vision) & Phase B (Business Architecture) — Conceptual Tier

DoDAF OV-1: High-Level Operational Concept

At the conceptual level, the enterprise operating environment consists of two distinct functional domains: 1. Digital-Work Domain: Governs enterprise communications, documentation, collaboration artifacts, and business processes. 2. Software-Delivery Domain: Governs source code repositories, code review workflows, issue tracking, continuous integration/continuous deployment (CI/CD) pipelines, and release evidence.

Rather than merging these platforms into a single database, the target operational architecture positions a User-Facing AI Orchestration Layer directly above established data planes. External systems of record, enterprise knowledge bases, and software engineering platforms connect across organizational trust boundaries via a centralized governance boundary.

Temporal Capability Note on Live Federation: Federated Model Context Protocol (MCP) connectors operate in a read-only mode by default (enabling search and context retrieval). State-changing write, update, and delete actions via federated MCP connectors are constrained to the early October 2026 product roadmap milestone.

DoDAF DIV-1: Conceptual Data Model

  • Knowledge Plane: Curated, structured, and unstructured enterprise information indexed for human discovery and AI retrieval-augmented generation (RAG).
  • Transaction Plane: State-changing application programming interfaces (APIs), event streams, and automated workflows.
  • Control Plane: Centralized enterprise capabilities for identity federation, access control, policy enforcement, secrets management, observability, and audit logging.
  • System of Record Authority: The single authoritative source for a given data domain (e.g., IT Service Management for change tickets, Software-Delivery Extension Platform for developer evidence, CRM for customer accounts).
  • Synced Model vs. Federated Model: The conceptual distinction between copying/indexing external data into a search index (Synced) versus querying authoritative endpoints dynamically at request execution time without persistent storage (Federated).

Actor Profile & Trust Matrix

  • Knowledge Worker: Interfaces with the AI orchestration layer via natural language to query systems and initiate tasks. Trust Level: User-delegated authorization context; constrained by Conditional Access and permission trimming.
  • Software Developer: Interacts with AI capabilities within development environments and reviews AI-generated pull requests. Trust Level: User-delegated developer identity; constrained by branch protection and repository access.
  • AI Administrator: Registers connectors, manages tool permissions, and grants tenant-wide consent. Trust Level: Elevated administrative privilege; scoped to service and connector management.
  • Platform/Integration Architect: Defines integration topologies, schema mappings, policy enforcement gateways, and tool catalogs. Trust Level: Design authority; no direct access to runtime data payloads.
  • External System of Record (e.g., ITSM, CRM, Observability Engine): Authoritative owner of domain data. Trust Level: External system; authenticated via least-privilege service credentials or scoped OAuth tokens.
  • Security & Compliance Officer: Monitors telemetry streams, enforces Data Loss Prevention (DLP), and reviews audit trails. Trust Level: Read-only compliance auditing and policy administration privileges.
  • Integration Server Operator (MCP Operator): Hosts and maintains tool integration endpoints. Trust Level: Production endpoint host; cataloged and constrained by enterprise execution policies.

Analytical Synthesis of Architectural Silences & Technical Constraints

  1. Licensing and SKU Dependencies: While source context specifies that custom connectors require Entra App Registrations and administrative consent, it remains silent regarding specific M365 E3/E5 tier requirements, Copilot capacity units, or Graph API volume consumption SKUs. Enterprise designs must treat connector billing as an open verification item.
  2. Government Cloud Capabilities: Synced connectors are confirmed across Commercial, GCC, GCC High, and DoD tiers. Conversely, federated MCP connectors carry the explicit constraint that availability "varies by federated connector." No confirmation is documented for air-gapped or Gov Secret enclaves.
  3. Data Retention Parameters: Although Purview controls and SIEM streaming are supported, specific platform default retention durations (e.g., 30, 90, or 365 days) for the Graph Semantic Index or Copilot session memory are unstated in the source context.
  4. Cross-Domain Entity Reconciliation: Conceptual architecture enforces the principle that systems of record remain authoritative and duplicate ownership must be avoided. However, the source text provides no automated reconciliation algorithm for resolving conflicting attributes across disparate platforms (e.g., matching a customer ID in CRM with an organization ID in GitHub).
  5. Extensibility Architecture Migration: The source context explicitly documents that the older GitHub App-based Copilot Extensions model has been deprecated in favor of Model Context Protocol (MCP) servers. Architectural blueprints must standardize on MCP servers for all future tool integration. Furthermore, federated MCP write capabilities must be flagged as a roadmap dependency targeted for early October 2026, enforcing read-only controls until that milestone is reached.
